# 《未来战争》选手端整改方案（分模块 TDD）

本文只定**怎么一块一块把分拉高**，不在本文里改策略代码。
规则以 `docs/任务书.md`、`docs/接口文档.md` 为准；实现以 `Demo/CoreGeek/` 为准。
真实失败样本：`Demo/CoreGeek/logs/teamB.log`（defender，第 1 夜英雄不在塔旁，基地被打穿）。

---

## 0. 为什么必须一块一块做

当前 bot 已经能出合法指令、能建 3 塔、能领任务。真正丢分的不是「整体不够聪明」，而是几条硬缺口按顺序把后面的分全掐死：

```text
入夜英雄不在塔旁
  → 3 座塔等于 0
  → 击杀分 ≈ 0，英雄被路上的机器人打死
  → 没人开火，墙再薄也会被拆
  → 基地第 1 天被毁，生存分后面 9 天全是 0
  → 后面的升级、炸弹、宝藏、自进化 SOP 都来不及兑现
```

积分结构（任务书第六章）：

| 分项 | 上限量级（粗算） | 当前对局（teamB） |
|------|------------------|-------------------|
| `score_3` 生存 | 10 天全活 ≈ **550** | 基地第 1 夜垮掉，后面全 0 |
| `score_2` 击杀 | 一夜几十只机器人，小 1 / 中 2 / 大 4 / BOSS 10 | 日志里总分只有个位数 |
| `score_1` 任务 | 每题约 50+ 加速奖；宝藏另算 | 开拓者卡在失败的 `acceptTask`；沙盒没读到题目文件 |

所以顺序只能是：**先活过第 1 夜 → 再让塔真正开火 → 再修墙拖时间 → 再修任务/LLM 去捡 `score_1` → 最后才做经济与对敌压榨。**

一口气改 `brain.py` 会把寻路、建墙、任务、LLM 缠在一起，红了不知道是哪块。下面每一片都是：**先写必红的测试 → 只改指定函数 → 绿了再进入下一片。**

## 1. 开发约定（每一片都照这个做）

工作目录：`Demo/CoreGeek`。跑测试：

```text
python -m pytest tests/test_<本片文件>.py -q
```

整包回归（每片结束后必须全绿，禁止「这片绿了、旧片红了」）：

```text
python -m pytest tests/ -q
```

### 1.1 一片的交付节奏

1. **Red**：只加测试文件（或只加测试函数），在当前 `main` 行为下**必须失败**。失败信息要能看懂缺的是哪条规则。
2. **Green**：只改本片「允许改的文件」，用最小实现让新测试过。
3. **Lock**：本片新测试全部 `@pytest.mark` 不用，但文件名/用例名保持稳定，作为后续片的回归网。
4. **停**：本片目标达成就停。不准顺手改下一片的函数，不准重构无关模块。

### 1.2 测试写法（统一夹具，不要新造世界）

- 继续用 `tests/conftest.py` 的 `make_payload`（基底是 `docs/request.txt`）。
- 需要「远离基地的工人 / 无墙 / 夜晚贴塔」时，在用例里改 `roundNo` 和 `teamOur.roles` 的 `pos`/`backpack`，不要复制一整份 JSON。
- 断言只锁**本片关心的动作**，不要把整张 `roleCommandMap` 拍成快照（否则下一片必碎）。
- 合法动作集合继续用现有 `VALID_ACTIONS`；`attack` 的 `controllerId` 必须是字符串。
- 每个用例开头不要依赖 `tasks.MEMORY` 的历史，`conftest` 已经按用例重置。

### 1.3 每片提交信息

```text
test(<片号>): <红测试在锁什么>
fix(<片号>): <最小实现>
```

不要把 8 片揉进一次提交。

## P1 — 入夜编制：天黑前必须往塔走

### 为什么是第一片

`teamB.log` 第 70 回合还是白天，工人在 `(15,14)` 一带 `move`；第 71 回合变黑夜，70 只机器人刷新，三个英雄仍在**往塔走**而不是开火。地图从中路走回右下基地大约 15 格，夜里走在机器人堆里等于送死。

现有 `_night` **已经**会「不在周围一格就走近塔」，但来不及。必须在**白天最后若干回合**停采、停远路买货，改成回防。

### 锁定的产品规则（写进测试，不要写进注释就完事）

1. 日内回合 `round_in_day >= 56`（白天最后 15 回合，含第 70）称为**回防窗口**。
2. 回防窗口内，工人不得 `collect` / `sell` / `buy`（已经站在塔周围一格除外）。
3. 回防窗口内，未贴塔的工人指令必须是 `move`，且这一步的切比雪夫距离相对「自己当前格 → 最近己方武器」是变近或持平（不允许往矿区走远）。
4. 开拓者若 **没有** `phaseTask`：回防窗口内不得 `acceptTask`，同样往最近武器走。
5. 开拓者若 **有** `phaseTask`：必须继续留在任务点（离开即任务结束，任务书 5.3）。本片不要让他回塔。
6. 白天前段（例如 `roundNo=10`）行为保持：该采矿仍采矿，**本片测试必须带一条反向用例**，防止回防逻辑污染全天。

常数建议：`RECALL_FROM = 56`，放在 `brain.py` 顶部。不要魔法数字散落。

### 红测试

新文件：`Demo/CoreGeek/tests/test_recall.py`

基底：`make_payload` 后把阵营改成需要的 `roundNo`，3 塔放在基地旁（`request.txt` 里 challenger 塔已在 `(9,24)/(10,25)/(9,25)`），工人挪到远处。

| `test_late_day_worker_steps_closer_to_tower` | 同上，3 塔在基地旁 | 走向矿 | `action=="move"`，且 `distance(下一步, 最近塔) < distance(当前, 最近塔)` |

先提交这些测试。在改 `brain.py` 之前跑 `pytest tests/test_recall.py`，前 3 条必须红。

### 最小实现（Green）

## P2 — 贴塔开火：夜里相邻就必须 attack

### 为什么单独一片

P1 解决「人在路上」。P2 锁定「人到了就要打」。`test_brain.py` 里已有「夜里可以 attack」，但太弱：不要求一定打出、不要求挂在武器 ID 上。

`teamB.log` 第 71 回合三个英雄全是 `move`，0 次 `attack`。P1 之后若人不贴塔，P2 测试仍用「已经站在塔旁」的构造，不依赖回防。

### 锁定规则

1. 黑夜、英雄切比雪夫距离塔 `<= 1`、塔 `cooldown==0`、射程内有 `health>0` 的机器人 → `roleCommandMap[塔ID].action == "attack"`。
2. `controllerId` 为该英雄 ID 的字符串。
3. 指令 key 是**武器 ID**，不是英雄 ID（英雄这回合可以没有自己的指令，这是合法的；监视器会报空闲，P2 不要为了消灭 idle 去给英雄再塞一条 `move`）。
4. 火箭 `cooldown>0` 不得 `attack`。
5. 白天仍然不得 `attack`（回归，已有用例可依赖）。

### 红测试

## P3 — 缺墙时必须采石头，不许去采高价矿

### 为什么现在才做墙

`test_defense.py` 已经锁了「人在墙边且包里有石头 → 建墙，不卖矿」。
`teamB.log` 里墙仍是 0，根因是另一种：墙没齐时 `_build_walls` 若够不着石矿会 `return False`，然后 `_mine` 按**小贩价格**排序，铜/铁永远排在石头前面。人被高价矿吸走，石头进不了包，墙就永远建不起来。

P1 回防会进一步减少白天采石时间，所以 P3 必须在「非回防窗口」把采石钉死。

### 锁定规则

1. `walls_missing` 非空，且该工人石头 `< STONE_KEEP`（现 4）：不得 `collect` 铜/铁。
2. 同上条件：若相邻石矿 → `collect` 该石矿；否则 `move` 靠近最近石矿。
3. 包里已有石头且相邻墙位 → `build` + `name=="wall"`（已有 `test_worker_builds_wall_when_towers_done`，不要破坏）。
4. 墙位已全部按 `_wall_order` 建完 → 恢复按价格采矿（已有 `test_worker_returns_to_selling_when_walls_done`）。
5. 回防窗口（P1）仍然优先回家：P3 用例一律用 `roundNo=20` 这类白天前中段，避免和 P1 打架。

### 红测试

新文件：`Demo/CoreGeek/tests/test_wall_stone.py`（不要往 `test_defense.py` 无限堆，那份专管朝向）

| 用例名 | 场景 | 当前 main 预期 | 通过标准 |
|--------|------|----------------|----------|
| `test_missing_walls_collect_stone_not_copper` | `roundNo=20`，3 塔已建，0 墙，工人在铜矿旁，石矿在别处，背包无石 | `collect` 铜 | 不得 collect 铜；`collect` 石或 `move` 向石矿 |
| `test_missing_walls_walk_to_nearest_stone_mine` | 工人不贴任何矿，石矿 `(4,24)`，铜矿更近 | 走向铜 | 下一步相对石矿变近 |
| `test_has_stone_builds_instead_of_more_ore` | 工人墙边，背包 `["stone"]` | 已有防御测试 | `build wall`；本片再锁一次防回归 |
| `test_walls_complete_allows_copper` | 按 `_wall_order` 把墙位都塞进 roles，工人铜矿旁 | 可采铜 | 允许 `collect` 铜 |

### 最小实现

**允许改**：`_build_walls`、必要时 `_mine` 增加 `prefer: str | None`。
**禁止改**：`_wall_order` 几何（已有朝向测试）、回防常数、商店。

推荐：`_build_walls` 在「没有石头且附近没有石矿」时不要 `return False` 把控制权交给 `_mine`，而是 `_walk_adjacent(..., 最近石矿)` 并 `return True`。

### 完成标准

- 白天前 55 回合，3 塔完成后工人会去石头而不是铜
- `test_defense.py` 朝向与「墙边直接建」仍绿

## P4 — 开拓者：停止对失效任务点空转

### 为什么

`teamB.log` 开拓者长时间停在 `(25,16)`，每回合 `acceptTask`，判题器一直 `lastRoundRoleActionResults[20011]=false`。这不是队伍异常（指令合法但没生效），但会：

- 浪费白天
- 入夜时人不在塔旁（和 P1 叠加）
- 任务冷却/`isValid=false` 时仍硬领

### 锁定规则

1. `playerTasks` 全部 `isValid==false`：不得 `acceptTask`。
2. 上回合该开拓者结果为 `false` **且** 本回合仍没有 `phaseTask`：本回合不得再发 `acceptTask`（允许 `move` 离开去回防或去商店）。
3. 有 `isValid==true` 的任务点，且人不在周围一格：`move` 靠近，到了再 `acceptTask`（现有逻辑保留）。
4. 已有 `phaseTask`：不得 `acceptTask`，不得离开周围一格（已有 `_run_task`）。
5. 本片不改沙盒命令内容（那是 P5）。

### 红测试

新文件：`Demo/CoreGeek/tests/test_pioneer_task_fsm.py`

| 用例名 | 场景 | 通过标准 |
|--------|------|----------|
| `test_no_valid_task_no_accept` | 两个任务 `isValid=false`，`coldDownRounds=30` | 开拓者无 `acceptTask` |
| `test_failed_accept_does_not_repeat_next_turn` | `lastRoundRoleActionResults[10011]=false`，`phaseTask=""`，人已在任务点旁 | 本回合不是 `acceptTask` |
| `test_valid_task_adjacent_accepts` | `isValid=true`，人在任务点旁，上回合成功或无记录 | `acceptTask` |
| `test_phase_task_does_not_leave` | `phaseTask` 非空，人已在旁 | 无 `move` 到距离任务点 >1 的格子 |

### 最小实现

**允许改**：`_try_accept_task`、`_pioneer_day`。
**禁止改**：`tasks.next_task_command`、prompt 文案。

建议：`_try_accept_task` 开头若 `not tasks: return False`（已有 note）；再加上 `turn.last_ok(role.unit_id) is False` 则本回合跳过领取，把控制权还给回防/宝藏/商店。

### 完成标准

- 失效任务点不再每回合刷 `acceptTask`
- P1 的「回防窗口不领任务」仍绿

## P5 — 沙盒 SOP：先读题目点名的文件

### 为什么

同一场 log 第 11 回合任务原文是：

```text
请阅读task_1_alpha.md，获取任务信息
```

现有 `_fallback_cmd`：

0. 把题目**字符串**写到 `/tmp/phase_task.txt`（写的是「请阅读…」，不是文件内容）
1. `pwd; ls; find`
2. `rglob` 列文件名
3. 把上次输出最后一行当答案

这会把 `ls` 的某一行提交成 `submitAnswer`，对应错误码 2，通过率 0。
自进化任务的积分公式对「部分正确」是按字段通过率给的；完全瞎交是 0，还可能提前结束题目。

### 锁定规则

1. `phaseTask` 里能用正则抽出文件名（`[\w./-]+\.(md|txt|json|py|csv)`）时，step 0 的 `executeCmd` 必须 **读取该文件**（`cat` 或 `python3` 打开），而不是只把题目原文 dump 到 `/tmp`。
2. 没有文件名时，才允许现有的「dump 题目 + ls」（兼容没有附件的题）。
3. `lastCmdResult` 以 `[exitCode:0]` 开头且正文不像目录列表时，才允许把正文收成 `pending_answer`；`ls`/`FILE ` 前缀的输出不得当作最终答案。
4. 有 `llmResp` 的 `executeCmd`/`taskAnswer` 时仍优先 LLM（已有测试，保持）。
5. 本片不增加 LLM prompt 次数逻辑（P6）。

### 红测试

扩 `Demo/CoreGeek/tests/test_tasks.py`（该文件已是 tasks 模块的 TDD 面，不要新开一套重复的 parse 测试）。

## P6 — LLM 额度：一天的 3 次不要在第 1–2 回合打光

### 为什么

接口：每个游戏日非任务期最多 3 次 LLM；任务期内不限且不计日额度。
`_maybe_prompt` 现在会在 `round_in_day==1` **或** `<=2 且情报不全` 时提问。`teamB.log` 第 1、2 回合连续发宝藏 prompt，当天额度立刻剩 1。后面几天的新传闻反而问不到。

任务期每回合都 `task_prompt` 是合法的（不受 3 次限制），P6 不要去「节省」任务期 prompt。

### 锁定规则

1. 无 `phaseTask` 时，每个 `day_index` 默认只发 **1** 次宝藏 prompt（建议只在 `round_in_day==1`）。
2. 例外：`lastSummonTreasureResult in (2, 3)` 允许再问（位置/物品错了需要纠偏）。
3. 不得因为「情报不全」在第 2 回合再问一次。
4. 有 `phaseTask` 时 `can_prompt` 仍恒为 True（已有测试）。
5. `errors` 含 code=5 时当天不再发非任务 prompt（已有）。
